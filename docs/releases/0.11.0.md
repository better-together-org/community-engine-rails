## Executive summary

`0.11.0` is a broad architecture-and-operations release.

At a high level it:

- turns Community Engine into a more clearly platform-aware and federated system
- adds stronger member data rights, consent, and privacy controls
- makes community access and membership-request review states clearer for both members and organizers
- continues the safety-reporting lane and adds content-security review states
- introduces tenant-safe inbound mail ingress as a new documentation-first runtime surface
- expands content, search, and MCP tooling for organizers and maintainers
- moves AI translation/runtime work toward persisted robot configuration and adapterized provider dispatch
- adds a built-in local-first bot-safety baseline for public intake plus first-party authorized robot scopes
- adds clearer governance, reviewer-evidence, and architecture-documentation surfaces for how CE is operated and audited
- adds short-link generation and share button surfaces so posts, pages, and events get a stable short URL and one-click clipboard share

This packet is intentionally evidence-heavy, but it should still be readable by people who are not tracking every PR. Each major section below explains what changed, why it matters, who is most affected, and where to go for deeper detail.

## How to review this branch

Although this branch is framed as the `0.11.0` release packet, the branch tip is not docs-only. Review is easier if the branch is treated as four linked slices instead of one undifferentiated delta:

1. **Release narrative and reviewer evidence:** `docs/releases/*`, `CHANGELOG.md`, diagrams, screenshots, sidecars, and review-packet guidance.
2. **Runtime and upgrade surface:** migrations, changed defaults, CI/runtime wiring, and release-hardening fixes that affect how host apps upgrade to `0.11.0`.
3. **Shipped product/runtime work:** platform scoping, privacy/data-rights flows, content-security/reporting, bot-safety baseline, inbound mail ingress, and related organizer/runtime surfaces.
4. **Implemented but intentionally gated or deferred work:** AI/robot runtime foundations and hidden block families that are present in code but not part of the normal organizer rollout path.

Operators preparing a release candidate should use the [0.11.0 release-manager checklist](0.11.0_release_manager_checklist.md) alongside this packet.

## 1. Federation, multi-tenancy, and platform scoping

This is the largest architectural shift in `0.11.0`. Community Engine now behaves as a platform-aware engine with host-platform context, platform-scoped data access, federated connections, mirrored content, and more explicit cross-platform consent boundaries.

**Why it matters:** This release stops treating CE like a single-site app with optional external links. Platform identity, scoping, trust, and cross-platform sharing are now first-class concerns in the engine itself.

**Who is affected:** stakeholders reviewing federation/governance posture, organizers configuring host platforms and trust relationships, and developers maintaining platform-aware behavior.

### Major shipped changes

- multi-tenant platform architecture and host-platform setup flows
- setup-wizard hardening to avoid duplicate host-platform creation and to block re-entry after completion
- federation platform connections and OAuth-backed trust
- mirrored pages, posts, and events with collision-safe identifier handling
- creator opt-in for public federated content export, plus grant-based private linked sharing
- platform-scoped metrics, messaging participants, notifications, and navigation fixes
- first-class storage adapter support for local, Amazon S3, and S3-compatible backends, with organizer-facing configuration UI
- community action network governance rules that connect agreements, publishing authority, robots, and shared-resource stewardship into one reviewable system (`#1494`)
- `content_feed` export hardened against a pathologically re-wrapped rich text body taking down an entire connection's feed with `SystemStackError` -- new `Seeds::SafeRichText` guard reads and bounds the raw stored HTML before any recursive ActionText method touches it, plus a per-record rescue in `FederatedContentExportService` so one bad record can't fail the whole page (2026-09 production incident)
- `platform_id` isolation rolled out across 20 model families beyond the initial cut (navigation, conversations/messages/agreements, categories, Joatu, reports/invitations, inbound email, webhooks, uploads, OAuth applications, activities, content blocks, person blocks, wizards, checklists, call-for-interests, person data exports/deletions) -- the linked upgrade guide below has not been refreshed for this expanded scope, see the note under Docs coverage
- RBAC platform-scoping remediation across 27 policy files, closing several unscoped `manage_platform`/`manage_platform_settings` checks -- most severely a cross-tenant `User`-account takeover (`#1762`, see section 10's Security notes)
- `new_platform_setup` wizard: a distinct, platform-scoped flow (6 steps, 4 PRs) for provisioning *additional* tenant platforms, separate from the singleton host-bootstrap wizard hardening described above
- Platform Domains admin UI (`PlatformDomainsController`), closing the prior Rails-console/rake-task-only gap for creating a platform with a chosen domain (`#1677`)
- Federation Hub: a new top-level nav destination showing any signed-in person their own content's federation status and connection health, plus a paginated activity feed
- per-platform multi-tenant sitemaps and dynamic, tenant-aware `robots.txt` -- includes a cross-tenant-indexing fix so one tenant's sitemap can no longer expose another tenant's content to crawlers

### Known limitation: federated content has no author attribution yet

Federation ships two separate consent layers, and only the first is complete in `0.11.0`:

- **Content-level consent (shipped):** `Person#federate_content` (default `false`) gates the export cursor -- a member's content is only ever eligible for federation after explicit opt-in.
- **Identity/attribution consent (not yet built, targeted v0.11.1):** even for opted-in content, exported posts/pages/events currently carry no author identity at all -- they arrive on the destination platform as unattributed records, with no deletion/correction path tied to the original author. This is tracked by issue `#1407` (closed, deliberately scoped to v0.11.1) and designed in `docs/plans/federation-consent-identity.md`.

`PlatformConnection` defaults to `pending` and requires explicit steward approval to activate (`PlatformConnectionsController#approve`) -- nothing turns on automatically. Platform stewards activating a connection in `0.11.0` should factor the missing-attribution gap into that decision.

## 4A. Built-in bot-safety baseline and authorized robot access

## 5. Inbound mail relay and tenant-safe routing

`0.11.0` introduces the first inbound-email relay path for CE using Action Mailbox plus Better Together routing contracts. **Why it matters:** Email ingress is a high-risk trust boundary. The release makes inbound routing more explicit, multi-tenant aware, and reviewable so host apps do not have to guess how mail should enter the platform.

**Who is affected:** operators wiring mail ingress, host apps providing mailbox subclasses, and maintainers responsible for inbound routing, persistence, and privacy posture.

### Major shipped changes

- inbound email relay MVP built on Action Mailbox and Better Together mailbox routing (`#1501`)
- tenant-safe routing and resolution services for mapping inbound mail to the correct platform context (`#1501`)
- persisted inbound email message records to support reviewable ingress behavior instead of transient-only mail handling
- host mailbox contract guidance that makes subclass requirements explicit for CE host apps

## 7A. Geography, hierarchy, and locatable entities

`0.11.0` adds PostGIS-backed geography hierarchy resolution: any geocoded Address, Building, or Event location now resolves to its containing Continent, Country, State, Region, and Settlement via polygon-containment queries, with ISO country-code and name-similarity fallbacks when no polygon match exists. This subsystem shipped without a dedicated section in earlier drafts of this packet — added here to close that gap.

**Why it matters:** Location data across the platform becomes queryable and filterable by administrative hierarchy, not just by raw coordinates, and reference-data records (settlements, regions, etc.) can now be individually privacy-scoped.

**Who is affected:** organizers managing location-bearing content (events, addresses, buildings), operators running the new boundary-import/backfill rake tasks, and developers extending `Geography::Placeable`.

### Major shipped changes

- PostGIS-backed hierarchy resolution job (`HierarchyResolutionJob`) connecting `LocatableLocation` to the full Continent → Country → State → Region → Settlement containment chain (#1667)
- Boundary-polygon import from Nominatim/Geocoder (`BoundaryImportJob`), plus operator rake tasks for boundary import, hierarchy backfill, and reference-data/seed-coordinate generation
- Redesigned, accessible location picker (mixed-type search, inline-create rows) replacing the prior radio-group type selector (#1781)
- `Geography::Map#platform_id` added, and `Geography::Map`/JOATU matching scoped to platform boundaries — closes a cross-tenant data-exposure gap (#1766)
- `privacy` column added to the geography and category reference-data tables, defaulting to `public` since these are admin/seed-managed records

## 9A. Short Links & Share Domain

`0.11.0` adds a link-shortener subsystem and a share-button UI component so posts, pages, and events can be shared externally with a stable, short URL and a one-click clipboard action.

**Why it matters:** Content sharing is a primary adoption path for community platforms. A stable short URL and clipboard share button reduce friction for members distributing community content outside the platform while keeping the share action within operator-controlled infrastructure rather than relying on third-party shorteners.

**Who is affected:** community members sharing content; organizers managing or reviewing short-link lifecycles; developers extending the `Shortlinkable` concern to new models.

### Major shipped changes

- `BetterTogether::ShortLink` model with configurable slug, polymorphic target, optional expiry, and click tracking (#1594)
- `Shortlinkable` concern: attach `has_one :short_link` + helper methods to any model with one `include` line
- Share button Stimulus `clipboard` controller — copies the short URL to clipboard with a visual confirmation state change
- Share button integrated on post, page, and event show views
- Platform-scoped short-link management view (`resources :short_links`, under the authenticated-user namespace — not community-nested)
- Public redirect at `GET /s/:code` — works without authentication; open redirect by design (scheme-validated `target_url`, platform-scoped lookup, no target-host allowlist)
- All views carry stable `dom_id`/`dom_class` DOM identifiers per the View DOM Identifier Standard
