# Upgrading a host app from 0.10.x to 0.11.0

Checklist for host apps that consume the `better_together` gem. It comes from rehearsing the NL Venues upgrade (CE 0.10.0 to `main`) on a copy of the production database, and was checked against the code on `main`.

Read it with the [0.11.0 release notes](0.11.0.md), the [release manager checklist](0.11.0_release_manager_checklist.md) and the [multi-tenancy upgrade guide](../upgrade/multi-tenancy-upgrade.md).

## Before you start

- Requirements: Ruby `>= 3.2`, Rails `>= 7.2, < 8.2`, PostgreSQL (see `better_together.gemspec`).
- Update the Gemfile constraint to `~> 0.11.0`, run `bundle update better_together`, then install and run the engine migrations (`rails better_together:install:migrations`, `rails db:migrate`). Take a database backup first. The release carries roughly 170 new migrations. They are guarded so a partially applied run can be retried, and `AlignHostCommunityPrivacyWithPlatform` is irreversible by design.
- Rehearse on a copy of the production database before upgrading production.

## Features that moved to extension gems

These shipped in 0.10.0 core and are not part of 0.11.0 core. Add the gem if the host app used the feature. None has a tagged release yet, so reference them from GitHub.

| Was in 0.10.0 core | Now | Add to the Gemfile | Configure |
|---|---|---|---|
| Elasticsearch indexing and search (`elasticsearch-model`, `elasticsearch-rails`) | [`better_together-elasticsearch`](https://github.com/better-together-org/better_together-elasticsearch) | `gem 'better_together-elasticsearch', github: 'better-together-org/better_together-elasticsearch', branch: 'main'` | Register host models with `BetterTogether::Elasticsearch.register_model_document` (see the gem's README). Core keeps only the generic search backend registry. |
| Sentry error reporting and browser snippet (`sentry-rails`, `sentry-ruby`) | [`better_together-sentry`](https://github.com/better-together-org/better_together-sentry) | `gem 'better_together-sentry', github: 'better-together-org/better_together-sentry', branch: 'main'` | `SENTRY_DSN`; `SENTRY_CLIENT_KEY` for the browser script. Registers the `:error_reporting` adapter. |
| Inline Google Analytics tracking hook | [`better_together-google-analytics`](https://github.com/better-together-org/better_together-google-analytics) | `gem 'better_together-google-analytics', github: 'better-together-org/better_together-google-analytics', branch: 'main'` | `GTAG_ID`. Listens for core's `better_together:share` browser event. |

The extension gems depend on `better_together >= 0.11.0` (Elasticsearch pins the exact core version), so they resolve only after the core upgrade.

## Changes that need host-app action

1. **Publishing agreement.** Migrations do not create the `content_publishing_agreement`. Until it exists and the acting person has accepted it, creating a public record fails with "The content publishing agreement must be accepted before this can be published." Run `rails better_together:generate:agreements` (`AgreementBuilder`; `CLEAR=1` rebuilds from scratch), then have each person who publishes accept it.
2. **Search.** Core search is Postgres-native (`pg_search`) and Elasticsearch is no longer a core dependency. Host models that declare `settings index: default_elasticsearch_index`, `mappings` or `as_indexed_json` fail at class load because `default_elasticsearch_index` no longer exists. Either move them to `searchable pg_search: { ... }` or install `better_together-elasticsearch` (table above). A model that includes `Searchable` without declaring a backend silently drops out of search.
3. **Migration file names.** `install:migrations` copies files without the underscore before digits (`phase_10` becomes `phase10`). Class names are unchanged, but host tooling that diffs by file name will report renames.
4. **Platform manager role and membership status.** Platform memberships carry a `status` (`pending` by default). A membership created without `status: 'active'` grants no permissions, so the user sees 404s. Host test factories and seed scripts that create memberships must set it. The CE factories use the role identifier `platform_manager` for the elevated role.
5. **Bot defense on forms.** Registration, sign-in, membership request and report forms enforce a minimum submit time. Feature specs that fill them must call `satisfy_bot_defense_minimum_wait(form_id)` (from `spec/support/better_together/bot_defense_test_helpers.rb`).
6. **`TrackPageViewJob`.** `perform` takes two more arguments: `perform(pageable, locale, platform_id = nil, logged_in = false)`. Update host code or specs that enqueue it.
7. **Platform URL.** Absolute redirects are built from the platform `url`. A platform whose `url` does not match the serving host raises `UnsafeRedirectError`; fix the platform record (and test setup) rather than the redirect.
8. **LLM client.** `ruby-openai` is replaced by `ruby_llm`. `OPENAI_ACCESS_TOKEN` is still honored as a fallback for `OPENAI_API_KEY`.
9. **Content Security Policy.** CE enforces the policy. CDN importmap pins (CE's own `mermaid` and `es-module-shims`, plus any in the host app) must be present in `script-src`; use the `CSP_*` environment variables. Storage-origin images need the image origin allowed too.
10. **MCP clients.** The MCP endpoint validates the `Origin` header against active `PlatformDomain` hostnames and internal platform URLs. Add hostnames for clients outside the platform with `MCP_ALLOWED_ORIGINS` (comma-separated); an empty list allows nothing.
11. **Rack::Attack behind a proxy.** Set `RACK_ATTACK_SAFELIST_NETWORKS` (comma-separated CIDRs) for load balancers and monitors, and make sure the proxy passes the client address in `X-Forwarded-For`. The safelist is only as reliable as `req.ip`.

## Privacy ceiling and private placeholder communities

A new record's `privacy` is capped by its platform and community (`PrivacyCeilingValidatable`): a record cannot be more open than its community. Host models that own a private placeholder community, for example a venue whose `PrimaryCommunity#primary_community_extra_attrs` sets `privacy: 'private'`, can no longer create public records. They fail with "Privacy cannot be more open than 'community'". Existing records stay valid because the validator runs only for new records and privacy changes.

Workaround: override `privacy_ceiling_exempt?` on the host model to return `true` (prepend it so it wins over the concern):

```ruby
module MyApp
  module VenuePrivacyCeilingExemption
    def privacy_ceiling_exempt?
      true
    end
  end
end

MyApp::Venue.prepend(MyApp::VenuePrivacyCeilingExemption)
```

Only do this when the model's visibility is governed by its own policy rather than by `privacy`. Reworking the ceiling so self-owned placeholder communities do not cap their record is tracked as a future assessment (see [#1830](https://github.com/better-together-org/community-engine-rails/issues/1830)).

## Host community privacy

`AlignHostCommunityPrivacyWithPlatform` sets each host platform's community to the platform's privacy, and the host community now follows the platform from then on. Before this, a public platform with a private host community answered 401 for the site logo and cover image to anonymous visitors and capped content in the host community. The migration is idempotent and cannot be reversed: restoring a private host community would break the host branding again.

## Verify after upgrading

- `rails db:migrate:status` shows no `down` migrations.
- Exactly one host platform exists and its `url` matches the serving host.
- An anonymous request for the site logo and cover image succeeds on a public platform.
- A person who accepted the publishing agreement can create a public record.
- Search returns results for each host model that declares a search backend.
- Sidekiq has only one worker generation running after the deploy (no stale `upcoming` containers on Dokku).
