# 0.11.0 Removed-Feature Cleanup Runbook

Repeatable procedure for fully removing a feature that was cut from the 0.11.0 release after already reaching one or more production host apps. Two cases have followed this pattern so far: Signal Protocol E2EE messaging (#1788, #1795) and Claim/Citation/EvidenceLink (#1799).

## The core problem

CE host apps (`communityengine.app`, `newfoundlandlabrador.online`, `sjcnl.btsdev.ca`, `borgberry.org`) pin the `better_together` gem to a commit SHA on `release/0.11.0-notes`, not a released tag (see `docs/releases/0.11.0_feature_gating_assessment.md` / the CE gem pinning strategy in `AGENTS.md`). A host can pick up a feature's migrations well before any tagged release exists. Deleting a feature's migration files from the gem does **not** un-apply them on a host that already ran them — their version rows stay in that host's `schema_migrations` table, and the DB objects they created stay in place unless something explicitly drops them.

Two ways a removal can go wrong:

1. **The removal ships no cleanup migration at all.** The tables/columns are simply abandoned in production, orphaned from the current codebase forever, with the deleted migration files no longer around to explain what created them. (This is what happened to Claim/Citation/EvidenceLink — the removal deleted the model/controller/view/migration source but never dropped the tables.)
2. **A later, unrelated migration still references the removed feature's tables/columns.** If that migration uses a guard like `column_exists?(table, :col)` without first checking `table_exists?(table)`, it crashes with `PG::UndefinedTable` on any host where the removed feature's tables never existed (a host that adopted the gem after the removal, or extracted the feature to a sibling gem before this migration ran). See #1795 (`better_together_joatu_settlements`, extracted to `better_together-borgberry`).

## Step-by-step

### 1. Confirm the actual removal shipped a cleanup migration

```bash
git show <removal-commit> --stat | grep db/migrate
```

No migration files listed → the removal is source-only; go to step 2. A migration listed → check whether it's idempotent (`if_exists:`/`table_exists?` guards) and skip to step 4 if so.

### 2. Verify the tables/columns are actually still live somewhere

Don't assume — check at least one production host directly:

```bash
SSH_AUTH_SOCK=/run/user/1000/keyring/ssh ssh dokku@<host> \
  "run <app> bin/rails runner \"puts ActiveRecord::Base.connection.table_exists?('<table>')\""
```

### 3. Audit for other migrations that reference the same tables

```bash
git log --all --oneline -S "<table_name>" -- db/migrate/
```

Anything dated *after* the removal that still names the table is suspect — check whether it was correctly rewritten to skip the removed feature (like #1795's later `add_platform_id_to_child_tables` migrations were, once patched) or whether it will crash on a host that never had the table.

### 4. Write one new idempotent cleanup migration on `release/0.11.0-notes`

Fresh timestamp, drops everything the removal should have dropped (FK-dependent tables first), guarded with `if_exists: true`. Do not try to resurrect or edit the deleted migration files — they're gone for a reason, and their version numbers may already be consumed on some hosts.

```ruby
class RemoveOrphanedFooSchema < ActiveRecord::Migration[7.2]
  def up
    drop_table :better_together_foo_children, if_exists: true
    drop_table :better_together_foo, if_exists: true
  end

  def down
    raise ActiveRecord::IrreversibleMigration
  end
end
```

Open a normal (non-draft) PR against `release/0.11.0-notes` for this — it's a real fix, not reintegration work.

### 5. Roll it out to every host, one at a time (T3 — explicit confirmation per app)

Per host, after the cleanup PR merges:

```bash
# 1. Bump the gem ref
#    Gemfile: ref: '<new release/0.11.0-notes tip>'
bin/dc-run bundle lock --update better_together
bin/dc-run bundle install

# 2. Pull in the new migration (copies with a host-local timestamp)
bin/dc-run bin/rails better_together:install:migrations

# 3. Apply it
bin/dc-run bin/rails db:migrate

# 4. Verify
bin/dc-run bin/rails runner "puts ActiveRecord::Base.connection.table_exists?('<table>')"
#   -> false

# 5. Boot/lint check, commit, push the host's rc/ce-0.11.0 branch
bin/dc-run bin/rails zeitwerk:check
bin/dc-run bundle exec rubocop --parallel
git add ... && git commit ... && git push <remote> rc/ce-0.11.0

# 6. Separately, with explicit per-app confirmation: deploy
SSH_AUTH_SOCK=/run/user/1000/keyring/ssh git push <dokku-remote> rc/ce-0.11.0:main
```

Serialize deploys per server — `communityengine.app` and `borgberry.org` share bts-3; `newfoundlandlabrador.online` and `sjcnl.btsdev.ca` share bts-5. Never run two deploys on the same host concurrently.

After each deploy, verify no stale `.upcoming-*` containers remain (`docker ps --filter name=<app>`), per the known Dokku deploy invariant in `AGENTS.md`.

### 6. If the feature has a reintegration branch open, update it too

A branch that reverts the removal commit will restore the *original* migration files. Once step 4's cleanup migration exists (or once it's actually deployed to any host), those original files become dead weight there — their versions are already marked `up` and Rails will never re-run them. Replace them with one new consolidated migration on the reintegration branch as well (same idempotent-guard pattern), so the branch stays internally consistent: single source of truth for the schema, no file that only "works" on a host that happens to be in exactly the right intermediate state.

## Known cases

| Feature | Removal commit | Had cleanup migration? | Cleanup PR | Reintegration branch |
|---|---|---|---|---|
| E2EE messaging | `fed1750adfd3` (#1788) | Yes, shipped with the removal | — | #1796 (consolidated) |
| Claim/Citation/EvidenceLink | `7909eea17` | No — this runbook's motivating case | #1799 | #1797 (consolidated) |

Audited (2026-09-18) against all other 0.11.0-era removal-pattern commits — no other gaps found. The `better_together-borgberry`/C3 Tree Seeds extraction (`219951f38`) is a deliberate permanent relocation to a sibling gem, not a "removed pending reintegration" case; its one fallout (an orphaned migration reference) was fixed by #1795 without needing a cleanup-migration-plus-reintegration-branch pair.
